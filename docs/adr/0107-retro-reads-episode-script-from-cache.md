# 0107. retro へ台本を渡し、台本をキャッシュに保存する

- ステータス: 採用
- 日付: 2026-08-15

## コンテキスト

自動改善ループ（ADR-0098）で retro が読むのは analyze の出力（findings・patterns）だけで、実セリフは届かない。analyze が拾い損ねた課題は retro から永久に見えず、拾えた課題も要約経由のため再発判定の根拠が薄い。

実際に、オープニングが「技術記事がない」と紹介した一方でニュースコーナーが記事を3本扱った回が出たが、改善ループはこれを拾わなかった。

ADR-0098 は「retro が中間ファイルを横断参照する」案を、`--force` で消え out-dir も利用者管理であることを理由に却下している。

## 決定

台本をキャッシュのエントリ（`corners[].lines`）へ保存し、retro プロンプトへ `{{scripts}}` として渡す。対象回は `analyses` と同じ（`retro.analysis_entries`）。

保存先をキャッシュにしたのは、既に回をまたぐ受け渡し口であり（ADR-0018 / ADR-0019）、番組ごとの状態ディレクトリ（ADR-0099）として利用者側で永続化済みだから。中間ファイルを参照しないため却下理由に当たらず、利用者リポジトリ側の対応も要らない。

1回分の台本は実測 1,300〜2,000 文字。既定 5 件でも約1万文字に収まるため、参照件数の設定は新設せず `analysis_entries` を共用する。

**台本を持つのは直近 `analysis_entries` 件だけ**とし、古いエントリからは `Compact` が落とす。retro が読むのは `Recent(entries, analysis_entries)` なので、範囲を一致させれば損失なく肥大化を避けられる。キャッシュには既に詳細ウィンドウ（直近 `cache.max_entries` 件）があり、その内側にもう一段狭い窓を置く形になる。

あわせて retro プロンプトを2点変える。

| 変更 | 理由 |
|---|---|
| 問題の根拠を `analyses` に加え `scripts` にも認める | 台本を渡しても「analyze が挙げた課題しか書けない」制約が残ると検出精度が上がらない |
| 事実の誤り・番組内容との矛盾（severity `high`）は単発でも採る | 反復を要求する既定のルールでは、1回でも十分な欠陥である矛盾が捨てられる |

文体・構成の課題に対しては反復重視の原則を維持する。

## 結果

analyze の要約が取りこぼした課題を retro が直接見つけられ、再発判定も実セリフを根拠にできる。

受け入れる制約:

| 制約 | 内容 |
|---|---|
| キャッシュが増える | 台本ブロックは実測 平均 6.6KB/件（1.1〜10.6KB）。直近5件のみ保持で `max_entries: 100` のファイルは 0.94MB → 0.97MB（+3.5%）。全件に持たせた場合は 1.58MB（+68%）になる |
| 台本は数回で消える | 保持範囲を出たエントリの台本は復元できない。参照範囲を後から広げても、遡って読めるのは広げた後に生成した回だけ |
| 過去回は台本を持たない | 追加前のエントリは `lines` が空。移行はせず以後の回から順次埋まる |
| プロンプトが長くなる | retro の LLM 呼び出しあたり約1万文字増 |

## 検討した代替案

- **台本を別ファイルへ保存する**: 保持期間・パス解決・ディレクトリ走査を再実装する。キャッシュの保持設定に相乗りするほうが安い。
- **利用者リポジトリが中間ファイルを保存する**: ADR-0098 の却下理由（`--force` で消える・out-dir が利用者管理）にそのまま当たる。
- **analyze の抽出精度を上げる**: 1回分の入力しか見ない制約は変わらず、複数回にまたがる取りこぼしの検出は retro でしかできない。
- **全エントリに台本を持たせる**: 後から参照範囲を広げたとき過去回も読めるが、95件ぶんは一度も読まれないまま 0.6MB を占める。
- **分析のメトリクスを削って相殺する**: 尺・発話レート・校正件数は timeline 由来で台本から復元できず、削っても 100 件で 101KB にしかならない。窓で肥大化が解けるため不要。

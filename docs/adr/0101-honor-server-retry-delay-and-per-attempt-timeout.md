# 0101. 429 のサーバー指示待機時間を尊重し、リトライのタイムアウトを試行単位にする（ADR-0051 改訂）

- ステータス: 採用
- 日付: 2026-08-02

## コンテキスト

ADR-0051 で 5xx/429 を指数バックオフでリトライする `Transport` を導入したが、待機は 1→2→4 秒（上限 8 秒）の固定値で、サーバーが返す待機指示は参照していなかった。

Gemini API はレート制限時に「51 秒後に再試行せよ」という指示を返す（`Retry-After` ヘッダではなくレスポンス本文の `google.rpc.RetryInfo`）。vox-radio はこれを読まず最大 7 秒で諦めるため、番組生成が 429 で失敗した。

さらに `http.Client.Timeout` はリトライの待機時間も含む全体に効くため、LLM クライアントの 60 秒設定のままでは長い待機を入れてもタイムアウトしてしまう。

## 決定

`internal/httpretry` を次のとおり変更する。

- **待機指示の尊重**: 429 のとき `Retry-After` ヘッダを優先し、無ければ本文の `RetryInfo.retryDelay` を読む。指示があればその時間だけ待ち、指数バックオフより優先する。
- **上限 60 秒**: 超える指示ならリトライせず 429 をそのまま返す（読み取り済み本文は `resp.Body` へ差し戻す）。
- **試行単位のタイムアウト**: `NewClient(timeout)` の `timeout` を `http.Client.Timeout` ではなく「1 試行あたりのタイムアウト」として各試行に context で適用する。
- 待機上限・リトライ回数はコード内定数のままとし設定 YAML 化はしない（ADR-0051 の方針を踏襲）。クォータ種別（分単位/日次）の判別も行わない。

## 結果

待てば回復するレート制限で処理を継続できるようになる。呼び出し側の変更は不要で、`httpretry` を使う LLM・VOICEVOX・記事収集すべてに透過的に効く。

トレードオフとして、汎用パッケージにベンダー固有（Google の `RetryInfo`）のパースが入る。ヘッダを優先するため、標準的な `Retry-After` を返す API にはベンダーに依らず効く。また LLM クライアントのタイムアウトの意味が「全体 60 秒」から「1 試行 60 秒」へ変わり、日次クォータの枯渇のように待っても回復しない 429 では失敗確定までの時間が延びる。

## 検討した代替案

- **`Retry-After` ヘッダのみ尊重する**: 実装は単純だが、Gemini は本文で待機指示を返すため今回の失敗を救えず却下。
- **LLM クライアント層で待機する**: 他クライアントへ横展開できず、ADR-0051 の「Transport に集約して透過適用」の方針に反するため却下。
- **`http.Client.Timeout` を待機込みの値へ引き上げる**: 変更は最小だが「1 リクエストの応答上限」の保証が失われるため却下。
- **日次クォータ超過を判別して即失敗させる**: 無駄な待機を避けられるが、判定を誤ると回復可能なケースまで落とすため見送った。
